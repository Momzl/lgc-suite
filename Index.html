-- Index critiques
CREATE INDEX idx_cal_dates ON calendar_days(property_id, date);
CREATE INDEX idx_bookings_dates ON bookings(check_in, check_out);
CREATE INDEX idx_bookings_status ON bookings(status);
CREATE INDEX idx_tasks_assigned ON tasks(assigned_to, scheduled_at);
CREATE UNIQUE INDEX idx_no_double_booking
  ON bookings (property_id, daterange(check_in, check_out, '[]'));

-- Partitionnement (scalabilité 10 000+ logements)
PARTITION bookings BY HASH (tenant_id);  -- 8 partitions
PARTITION calendar_days BY RANGE (date);  -- mensuel

-- Contraintes de sécurité
ALTER TABLE audit_logs ADD CONSTRAINT audit_append_only
  CHECK (TRUE);  -- Trigger BEFORE UPDATE/DELETE → RAISE EXCEPTION

4 Fiabilité synchro OTA (Module 7)

Architecture à 5 couches garantissant un taux de succès ≥ 99.9% et une prévention totale du double booking.

LAYER 1 — Webhooks entrants (push temps réel)
├── Endpoint dédié par OTA, signature HMAC-SHA256
├── Réponse 200 immédiate (< 2s) → traitement BullMQ
├── Idempotence : event_id unique → Redis TTL 24h
└── Log de chaque webhook reçu

LAYER 2 — File BullMQ (asynchrone)
├── Priorités : réservations > annulations > modifs > tarifs
├── Retry exponentiel : 1s, 4s, 16s (3 tentatives)
└── Dead Letter Queue + alerte admin si échec final

LAYER 3 — Circuit Breaker (par OTA)
├── CLOSED (normal) → OPEN (5 échecs) → HALF-OPEN (60s)
└── Alerte Datadog à chaque bascule

LAYER 4 — Polling de sécurité (filet)
├── Toutes les 15 min : re-pull des calendriers OTA
└── Correction automatique des désynchronisations

LAYER 5 — Monitoring + Alertes
├── Dashboard Datadog par plateforme
├── Alerte si succès < 99% sur 5 min
└── Rapport quotidien automatique

DOUBLE BOOKING — Protection ultime
├── Lock pessimiste PostgreSQL (SELECT FOR UPDATE)
├── Contrainte UNIQUE base (property_id, daterange) EXCLUDE
├── Vérification avant confirmation
└── Si détecté : annulation la + récente + remboursement + email

5 Flux réservation 100% automatisé (Module 5)

ÉTAPE 1 — Réception webhook OTA
  ├── Vérification signature HMAC
  ├── Idempotence check (event_id Redis)
  ├── INSERT booking status=PENDING
  └── Lock pessimiste sur dates

ÉTAPE 2 — Blocage calendrier (< 30s)
  └── Push sync vers toutes les OTA connectées

ÉTAPE 3 — Paiement (résa directe uniquement)
  ├── PaymentIntent Stripe + idempotency_key
  ├── 3D Secure si requis
  └── Retry J+1, J+2, J+3 si échec

ÉTAPE 4 — Documents
  ├── Contrat PDF (variables réservation injectées)
  ├── Facture PDF
  └── Dossier voyageur S3 (lien signé 7j)

ÉTAPE 5 — Communications auto
  ├── Email confirmation (i18n auto)
  ├── SMS Twilio
  ├── Push propriétaire + conciergerie
  └── Mission ménage J-1 planifiée

ÉTAPE 6 — J-1 check-in 10h
  ├── Code serrure IoT généré (Nuki/August/Yale)
  ├── Guide voyageur PDF
  └── Code accès (email + SMS + WhatsApp)

ÉTAPE 7 — Jour J check-in
  ├── Code serrure activé à l'heure
  └── Statut → CHECKED_IN

ÉTAPE 8 — Check-out
  ├── Code serrure désactivé auto
  ├── Mission ménage déclenchée
  └── Délai caution 72h démarre

ÉTAPE 9 — J+1 post-séjour
  ├── Demande avis
  ├── Facture finale
  └── Libération caution J+3

EXCEPTIONS 100% AUTOMATIQUES
├── Double booking → annulation + remboursement + email excuse
├── Paiement échoué → retry 3x puis annulation
├── API serrure down → code boîte à clés par SMS
└── Webhook manqué → re-pull 15 min

7 Paiements PCI-DSS (Module 8)

CONFORMITÉ : PCI-DSS SAQ A (délégation totale Stripe)
Aucune donnée carte ne transite par nos serveurs.

FLUX PAIEMENT
1. Client → Stripe Elements → tokenisation client
2. Backend reçoit PaymentMethod ID (jamais PAN)
3. PaymentIntent + idempotencyKey = reservation_uuid
4. 3D Secure automatique
5. Webhook payment_intent.succeeded → update booking

CAUTION (empreinte)
├── SetupIntent avant check-in
├── Empreinte AUTORIZED (pas débitée)
├── Libération auto J+3 post-checkout (cron)
└── Capture partielle si litige (photos preuve)

SÉCURITÉ WEBHOOKS
└── stripe.webhooks.constructEvent(payload, sig, secret)
    + idempotence Redis par event_id

MONITORING
├── Succès paiements (alerte < 99.5%)
├── Alerte paiement > 5000€ échoué
└── Réconciliation quotidienne Stripe ↔ DB
